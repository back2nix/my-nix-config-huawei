# Claude и Codex с изолированной сетью

Команды `claude-{1082,1088,1090}-safe` и `codex-{1082,1088,1090}-safe` сохраняют рабочую директорию, домашний каталог,
файлы и переменные окружения пользователя. Bubblewrap создаёт обязательные
user/network/PID namespaces, убирает capabilities и запрещает новые user
namespaces. Внутри доступен только loopback: внешних интерфейсов и маршрутов нет.
Ошибка изоляции завершает запуск, перехода к обычному агенту нет.
Codex автоматически получает `--no-daemon`; повторный явный флаг удаляется.
Сокращения fish `claude` и `codex` запускают только safe-варианты.

Для пар 1088 и 1090 используются отдельные фиксированные входы 1095
(Франкфурт) и 1097 (Astana), DNS также идёт через соответствующий туннель.

Два пользовательских relay через временные UNIX-сокеты соединяют:

- `127.0.0.1:1083` внутри с `127.0.0.1:1093` на хосте;
- `127.0.0.1:6443` внутри с локальным Kubernetes API на хосте.

Вход sing-box `http-claude-safe` на 1093 имеет фиксированный выход `ssh-out1`
(Сеул), без selector и fallback в direct. DNS целевых доменов использует
Quad9 DoH через этот же выход. Переключение `proxy-mode` его не затрагивает.
Суффикс 1082 связывает имя команды с существующей парой команд; защищённый
вариант сознательно не следует переключаемому маршруту обычного `claude-1082`.

HTTP(S)/ALL_PROXY установлены на внутренний 1083, NO_PROXY содержит только
loopback. Команды, игнорирующие прокси, не имеют прямого выхода. UDP и прямой
DNS также не выходят из namespace. Не все инструменты автоматически используют
HTTP-прокси: например, SSH потребует отдельного ProxyCommand.

## k3s

Стандартный `/etc/rancher/k3s/k3s.yaml` с сервером
`https://127.0.0.1:6443` работает без изменения kubeconfig и без отключения TLS.
Другой адрес API (например, `10.0.0.1`) нужно заменить на loopback в отдельном
kubeconfig с подходящим сертификатом. Автоматически kubeconfig не изменяется.
Доступны API, logs, exec и port-forward через API. Port-forward слушает внутри
namespace и недоступен из браузера хоста; к Pod/Service IP напрямую доступа нет.

## Применение и проверка

После обычного `nixos-rebuild switch --flake .#huawei`:

```sh
claude --check
codex --check
claude
codex --yolo
```

`--check` проверяет запрет прямого HTTPS к IPv4/IPv6, запрос через фиксированный
прокси (печатает IP выхода) и `/version` локального k3s с текущим kubeconfig.
Полная проверка требует работающих sing-box, туннеля и k3s.
При выключенном sing-box запрос через прокси должен завершиться ошибкой,
прямой выход появляться не должен. Эта проверка не выключает службы сама.

## Граница защиты

Это изоляция прямой IP-сети процессов, а не защита от намеренного обхода
через полный доступ к компьютеру. Файловая система и её UNIX-сокеты доступны:
Docker/containerd, пользовательский systemd/D-Bus и другие службы способны
запускать операции вне namespace. Сетевые запросы через `kubectl exec` или
созданные Pod идут из сети кластера; для них нужны отдельные политики k3s.
Не считать такую конфигурацию гарантией против этих способов обхода.

Реализация: `module/claude-safe.nix`, вход и DNS: `sops/sops.nix`.
