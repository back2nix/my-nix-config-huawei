# Claude и Codex с изолированной сетью

Команды `claude` и `codex` запускают `claude-safe` и `codex-safe`.
Они сохраняют рабочую директорию, домашний каталог, файлы и переменные
окружения пользователя. Bubblewrap создаёт обязательные user/network/PID
namespaces, убирает capabilities и запрещает новые user namespaces.
Внутри доступен только loopback: внешних интерфейсов и маршрутов нет.
Ошибка изоляции завершает запуск, перехода к обычному агенту нет.
Codex автоматически получает `--no-daemon`, если флаг ещё не указан.

Два пользовательских relay через временные UNIX-сокеты соединяют:

- внутренний `127.0.0.1:1101` Claude с HTTP-входом 1101 на хосте,
  а внутренний `127.0.0.1:1103` Codex — с HTTP-входом 1103;
- внутренний `127.0.0.1:6443` с локальным Kubernetes API на хосте.

У каждого агента собственный selector: USA, USA через Casino, FRA или KZ.
Direct отсутствует. Маршрут меняется через отдельное меню VPN, `claude-proxy`,
`codex-proxy` или `vpn-route`; выбор сохраняется в sing-box.
DNS целевых доменов использует Quad9 DoH через тот же selector.
Исключение: HTTP/HTTPS-запросы через прокси к `10.0.0.1` и его точным
алиасам из `networking.extraHosts` (например, `casino.local`) идут с хоста
на `10.0.0.1`, без VPN и внешнего DNS. Порт назначения сохраняется.
Это исключение действует также для фиксированных safe-команд.
Переключение общих портов через `proxy-mode` агентов не затрагивает.

Фиксированные `claude-{1082,1088,1090}-safe` и `codex-{1082,1088,1090}-safe`
сохранены для совместимости: их входы 1093/1095/1097 имеют фиксированные
выходы Сеул/Франкфурт/Astana и не следуют выбору маршрута приложения.

HTTP(S)/ALL_PROXY установлены на выделенный внутренний порт (Claude — 1101,
Codex — 1103; фиксированные safe-команды — 1093/1095/1097), NO_PROXY содержит только
loopback. Команды, игнорирующие прокси, не имеют прямого выхода. UDP и прямой
DNS также не выходят из namespace. Не все инструменты автоматически используют
HTTP-прокси. Для SSH обёртка автоматически задаёт ProxyCommand через
UNIX-сокеты с фиксированными адресами и портом 22.
Для локальных веб-сервисов используй обычный `curl http://10.0.0.1:ПОРТ`
или `curl http://casino.local:ПОРТ`, без `--noproxy`: доступ обеспечивает прокси.

## k3s

Стандартный `/etc/rancher/k3s/k3s.yaml` с сервером
`https://127.0.0.1:6443` работает без изменения kubeconfig и без отключения TLS.
Другой адрес API (например, `10.0.0.1`) нужно заменить на loopback в отдельном
kubeconfig с подходящим сертификатом. Автоматически kubeconfig не изменяется.
Доступны API, logs, exec и port-forward через API. Port-forward слушает внутри
namespace и недоступен из браузера хоста; к Pod/Service IP напрямую доступа нет.

## Dev-серверы агента

Сервер, запущенный `claude` внутри namespace на порту 3917, 3918 или 3919,
доступен с хоста по `http://localhost:ПОРТ` (браузер, chrome-devtools).
На хосте порт слушает только 127.0.0.1. Пока идёт сессия `claude`, эти порты
на хосте заняты; во второй одновременной сессии проброс не поднимется
(ошибка в логе `dev-ПОРТ-host.log`). Список — `devPorts` в `module/claude-safe.nix`.

## Применение и проверка

После применения flake-профиля своего устройства:

```sh
claude --check
codex --check
claude
codex --yolo
```

`--check` проверяет запрет прямого HTTPS к IPv4/IPv6, запрос через выбранный
прокси (печатает IP выхода) и `/version` локального k3s с текущим kubeconfig.
Полная проверка требует работающих sing-box, туннеля и k3s.
При выключенном sing-box запрос через прокси должен завершиться ошибкой,
прямой выход появляться не должен. Эта проверка не выключает службы сама.

## Граница защиты

Это изоляция прямой IP-сети процессов, а не защита от намеренного обхода
через полный доступ к компьютеру. Файловая система и её UNIX-сокеты доступны:
Docker/containerd, пользовательский systemd/D-Bus и другие службы способны
запускать операции вне namespace. Сетевые запросы через `kubectl exec` или
созданные Pod идут из сети кластера; для них нужны отдельные политики k3s.
Не считать такую конфигурацию гарантией против этих способов обхода.

Реализация: `module/claude-safe.nix`, вход и DNS: `sops/sops.nix`.

Полная схема маршрутов: [proxy-cli.md](proxy-cli.md).

## Диагностика relay

Ошибки `socat` сохраняются отдельно для прокси, k3s и каждого SSH-направления,
с метками `inside`/`host` для сторон relay. Каталог сессии находится в
`${XDG_STATE_HOME:-$HOME/.local/state}/codex-safe/relays/session.*`
(для Claude — `claude-safe`, для фиксированных команд — имя команды).
При завершении сессии с ошибками обёртка печатает путь к логам;
сессии без ошибок удаляются. Логи ошибок сохраняются до ручного удаления.
`Connection reset by peer` само по себе не определяет первопричину:
нужно сопоставить файл relay с журналом sing-box и поведением агента.

## SSH к разрешённым серверам

Внутри всех safe-команд `ssh` использует отдельный временный конфиг,
который затем включает `~/.ssh/config`: пользователи, ключи и проверка
ключей серверов сохраняются. Список хостов хранится в sops-секрете
`claude-safe/ssh_endpoints` (не в git), по строке на хост:
`имя адрес [алиас...]`. Хост доступен по имени, адресу и алиасам, только порт 22.
После `nixos-rebuild switch` изменения подхватит следующий запуск safe-команды. Другие адреса и порты не открываются.
Вызов абсолютного `/run/current-system/sw/bin/ssh` обходит обёртку и не
получает этот доступ; используй обычный `ssh АЛИАС`.

SSH работает независимо от VPN-прокси агентов. Поэтому он остаётся доступным
при обрыве этого прокси. SSH-туннели и команды на удалённых серверах могут
обеспечить обход защиты; разрешённые SSH-соединения не блокируются при обрыве VPN.
После пересборки нужно завершить старые safe-сессии и запустить агенты заново.
