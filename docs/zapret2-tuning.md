# zapret2: как подбирать стратегии обхода ТСПУ

Документ для человека или агента, которому нужно починить прямой (без прокси)
доступ к сайтам из `module/zapret2/hosts.txt`. Что такое zapret2 в этой
конфигурации и чего он не делает — в шапке `module/zapret2.nix`.

## Коротко

```
just zapret-check        # что сейчас не открывается напрямую (без root, ничего не меняет)
just zapret-tune         # перепроверить прошлые решения, подобрать заново только сломавшееся (~3 мин)
just zapret-tune --full  # с нуля, включая unknown и flaky (10+ мин)
just switch              # применить
```

Во время `just zapret-tune` не запускать `just switch`: он поднимет службу,
замеры смешаются, скрипт прервётся.

## Файлы

| Файл | Что это | Кто правит |
|---|---|---|
| `module/zapret2/hosts.txt` | домены, для которых нужен обход | человек |
| `module/zapret2/candidates.txt` | стратегии-кандидаты по приоритету | человек |
| `module/zapret2/probe-hosts.txt` | необязательный: какой хост проверять вместо `домен` и `www.домен` | человек |
| `module/zapret2/tune-state.txt` | решение по каждому домену, память между запусками | только `just zapret-tune` |
| `module/zapret2/profiles.json` | какая группа доменов какой стратегией обходится | только `just zapret-tune` |
| `scripts/zapret2-tune.sh` | подбор | — |
| `module/zapret2.nix` | собирает из `profiles.json` конфиг nfqws2 | — |

## Главное, что нужно знать

**Одной стратегии на все домены нет.** Стратегия, которая чинит один сайт,
ломает другой, в том числе незаблокированный. Замеры 2026-11-16 на этой сети:

- Кэшам YouTube у провайдера (`rrN---sn-*.googlevideo.com`) фальшивый
  ClientHello ломает TLS, работает только нарезка без фальшивки.
  Симптом был: youtube.com открывается, видео не грузится.
- Discord и X наоборот: без фальшивки не открываются.
- Старый конфиг применял фальшивку ко всему списку и этим ломал сайты, которые
  открываются вообще без обхода (например, `mozilla.org`: 0 из 10 с обходом).
- Большинство доменов списка (185 из 281) открываются без обхода вовсе.

Поэтому подбор идёт по каждому домену отдельно, а результат — несколько
профилей nfqws2, каждый со своим списком доменов.

**Проверять нужно тот хост, который реально блокируют.** У CDN витрина и узлы
раздачи блокируются по-разному: `www.youtube.com` открывался, а видеосервер нет.
Для YouTube скрипт сам узнаёт имя кэша провайдера (спрашивает у
`redirector.googlevideo.com/report_mapping` и переводит код площадки в
`sn-`имя). Для других CDN — вписать узел в `probe-hosts.txt`:

```
# домен  хост [хост...]
discord.media  some-node.discord.media
```

Как узнать узел: открыть сайт через прокси, в DevTools → Network посмотреть,
с какого хоста идёт то, что не грузится.

**Сеть шумит под нагрузкой.** Десятки параллельных запросов к заблокированным
адресам дают ложные отказы: при 32 потоках «не открывались» Discord и YouTube,
которые через пять минут открывались 6 раз из 6. Поэтому в скрипте 3 потока, а
упавшие перепроверяются по одному. Отдельным замерам верить только после повтора; сомнение
проверяется руками, по одному запросу:

```
for i in 1 2 3 4 5 6; do
  curl -4 -s -o /dev/null --noproxy '*' --max-time 4 -w '%{http_code} ' https://ХОСТ/
done
```

`000` — TLS не прошёл. Любой другой код, включая 403/404, значит «не заблокировано».

## Группы доменов

| Группа | Смысл | Что делает zapret |
|---|---|---|
| `direct` | открывается без обхода | не трогает |
| имя стратегии | закрыт, с этой стратегией открывается, и это подтвердилось повторно | профиль этой стратегии |
| `flaky` | мерцает сам по себе, решение не воспроизводится | не трогает |
| `unknown` | закрыт, ничего не помогло, либо на tcp/443 никого нет | профиль первой стратегии, как было исторически |

**Мерцающие сайты.** Часть сайтов (на 2026-11-16 — Fastly и CloudFront:
`trello.com`, `debian.org`, `gnome.org`, `githubusercontent.com`, `atlassian.com`)
без всякого обхода за секунды переходит из «открыт» в «закрыт» и обратно:
четыре запроса подряд к одному IP дают `200 000 000 000`. Обход им не помогает
— их режут периодами, а не по имени. Пока скрипт этого не различал, каждый
прогон раскладывал их по-новому: случайно «закрыт», потом случайно «починен»
очередной стратегией. Отсюда правило: решение «закрыт, лечится стратегией X»
принимается, только если повторилось (см. шаги 4 и 6 ниже). Таким сайтам для
стабильной работы нужен тоннель.

## Что делает `just zapret-tune`

Останавливает службу, поднимает свою таблицу nft и свою очередь (со службой не
пересекается), берёт nfqws2 и lua из установленного юнита. Дальше:

1. Выбирает для каждого домена живой хост (`домен` или `www.домен`, кто ответил
   на tcp/443) и дальше проверяет только его. Не ответил никто — домен в
   проверках не участвует, прошлое решение сохраняется.
2. Без обхода: прошлые `direct` и новые домены. Открылся — `direct`.
3. Все прошлые стратегии одним запуском, как в службе. Открылся — решение в силе.
4. Второй взгляд без обхода на всё, что не прошло шаги 2–3. Открылся сам —
   `flaky`, по стратегиям не гоняется.
5. Подбор для оставшихся: по очереди каждая стратегия из `candidates.txt`,
   проверяются только домены, которым ещё не нашлось рабочей.
6. Подтверждение новых решений: под итоговым набором профилей домен должен
   открыться ещё раз, а без обхода — по-прежнему быть закрытым. Иначе `flaky`.
7. Пишет `tune-state.txt` и `profiles.json`, возвращает службу как была.

`unknown` и `flaky` в обычном запуске пропускаются: это самые дорогие домены
(каждая попытка — полный таймаут на каждой стратегии). Их перепроверяет `--full`.

Предохранитель: если стратегию разом потеряла треть доменов, файлы не пишутся.

Критерий «открывается» — завершённый TLS-handshake напрямую, по IPv4 (HEAD-запрос,
тело не качается). Скорость после handshake скрипт не меряет: замедление (а не
блокировку) он не увидит. Если сайт открыт, но тормозит и обход ему помогает, —
вписать его группу в `tune-state.txt` руками и запустить `just zapret-tune`.

### Сколько это занимает и почему

Первая версия шла больше получаса, нынешняя — около 3 минут на 281 домен.
Что дало выигрыш, по убыванию:

- не гонять по стратегиям открытые сайты: им обход не нужен, а их таймауты
  под неподходящей стратегией съедали основное время;
- помнить прошлые решения и перепроверять их одним запуском, а не подбирать заново;
- пропускать `unknown` и `flaky`;
- один хост на домен вместо двух;
- HEAD вместо GET;
- второй взгляд перед подбором (шаг 4).

Чего делать нельзя ради скорости — поднимать параллельность. Замеры на этой сети:

| Потоков | Результат |
|---|---|
| 32 | «упали» Discord и YouTube, через пять минут открывавшиеся 6 из 6 |
| 8 | два прогона подряд разложили домены по-разному |
| 6, перепроверка тоже пачкой | 27 открытых сайтов записаны в закрытые |
| 3, перепроверка по одному | стабильно |

## Если ни один кандидат не подошёл

Домен в `unknown`, но сайт точно существует и через прокси открывается.

1. Убедиться, что это не блокировка по IP — тогда zapret бессилен, нужен тоннель:

   ```
   ping -c2 ХОСТ
   curl -4 -s -o /dev/null --noproxy '*' --max-time 5 -w '%{http_code}\n' http://ХОСТ/
   ```

   TCP на 443 не соединяется вовсе (`time_connect` = 0) — блокировка по адресу.
   Соединяется, но TLS не проходит — блокировка по содержимому, zapret может помочь.
2. Полный перебор: `just zapret-blockcheck ХОСТ`. В конце печатает рабочие
   наборы `--lua-desync=...`.
3. Выбрать самый простой из рабочих, дописать строкой в `candidates.txt`
   (ниже существующих, чтобы не менять раскладку остальных), повторить
   `just zapret-tune`.

Гипотезу о конкретной стратегии можно проверить без перебора — так была
найдена причина с YouTube: взять рабочую для большинства стратегию, убрать или
заменить в ней одну часть, сравнить на двух хостах с разным поведением.

## Чего здесь нет

- **QUIC (udp/443).** На 2026-11-16 напрямую не проходил никуда, включая
  домены вне списка; профиль `quic` в модуле не подбирался. Браузер откатывается
  на TCP.
- **Не-443 и не-TLS.** Голос Discord, Telegram MTProto и т. п. под правила не
  попадают.
- **Трафик через прокси.** zapret видит только то, что уходит с ноутбука
  напрямую; соединения sing-box к серверам тоннелей исключены в nft.
